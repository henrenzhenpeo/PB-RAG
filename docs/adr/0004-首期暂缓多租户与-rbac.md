# ADR 0004：首期暂缓多租户与 RBAC

- 状态：已接受
- 日期：2026-11-04
- 影响范围：六周核心版本的身份、授权与 Workspace 语义

## 背景

PB-RAG 当前最重要的目标是完成文档入库、Production RAG、可追溯引用、Agent Runtime、评测与故障恢复的端到端闭环。多租户、用户成员关系和 RBAC 会引入身份模型、权限矩阵、认证流程和大量隔离测试，但不会直接验证 RAG 与 Agent 的核心机制。

## 决定

- 六周核心版本采用单用户、单部署模式；
- 暂不实现用户、成员关系、角色、API Key 权限范围、Workspace RBAC 和 MyBatis-Plus TenantLine 插件；
- Workspace 保留，但只表示知识资源的逻辑分组，不表示租户或授权边界；
- `workspace_id`、路径中的 `workspaceId` 与数据库复合外键继续保留，用于资源归属、查询约束、引用一致性和防止错误关联；
- 首期不把“使用 Workspace A 的路径无法读取 Workspace B 的资源”宣传为授权能力，它只是资源定位行为；
- 工具白名单、Schema 校验、审批、超时、审计、敏感信息处理、SSRF 与 Prompt Injection 防护不因本决定而延期；
- 在完成 RAG、Agent Runtime 和评测闭环后，如出现团队协作或对外服务需求，再为身份与授权单独设计 ADR。

## 理由

这一取舍减少了与当前学习目标关系较弱的功能宽度，使开发时间集中在检索质量、引用、异步任务、Agent 循环、可观测和评测上。保留 Workspace 数据结构可以继续支持多个知识集合，也避免未来需要多租户时进行破坏性数据迁移。

## 影响

- 当前系统不能作为多个互不信任用户共同使用的 SaaS；
- API 没有用户级访问控制，部署边界本身承担访问限制；
- 代码和文档应使用“Workspace 资源分组/作用域”，避免使用“租户隔离/权限隔离”描述现有能力；
- 未来加入授权时，必须在检索和工具执行前由确定性代码执行，并补齐跨租户集成测试。

## 验证

- 入库、检索、引用和 Trace 均保留正确的 `workspace_id`；
- 数据库复合外键拒绝把资源关联到错误的 Workspace；
- 不引入 TenantLine、用户表、成员表或角色表；
- 六周验收不再包含 RBAC 与跨租户越权测试。
